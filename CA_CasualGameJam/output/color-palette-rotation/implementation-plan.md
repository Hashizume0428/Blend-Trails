# 5ステージごとの色の組み合わせ切り替え：実装検討メモ

作成日：2026-10-24

状態：2026-10-24にユーザーの回答で仕様の3点を確定。2026-10-25の実装依頼を受けて実装・検証を完了。EditMode全46件・PlayMode全42件が成功。

## 1. 確定した仕様

要望：従来の赤・青・紫に加え、赤・黄・オレンジ、青・黄・緑を使用し、5ステージごとに組み合わせをローテーションする。線の操作、混色、正解判定の考え方は維持する。

以下の3点はすべてユーザー確認済み。

1. チュートリアルを含むStage1〜5を赤・青・紫、6〜10を赤・黄・オレンジ、11〜15を青・黄・緑とし、16以降は同じ順で繰り返す。
2. 盤面・開始点の位置・解答経路を維持し、旧赤を第1色、旧青を第2色、旧紫を混色として置き換える。
3. Stage31以降も画面のStage番号を基準にする。抽選された問題の元の番号には依存させない。

確定した対応表：

| 表示Stage番号 | 旧赤の役割 | 旧青の役割 | 旧紫の役割 |
|---|---|---|---|
| 1〜5 / 16〜20 / 31〜35 … | 赤 | 青 | 紫 |
| 6〜10 / 21〜25 / 36〜40 … | 赤 | 黄 | オレンジ |
| 11〜15 / 26〜30 / 41〜45 … | 青 | 黄 | 緑 |

判定も現在の意味を引き継ぐ：通常マスはそのステージで使う基本2色のどちらか単色のみ正解。混色を描く操作自体は可能だが、通常マスの混色は不正解。色指定は完成色との完全一致、禁止色も完成色との比較とする。リロード・巻き戻し・キャンセルは対象の基本色だけを除去する。3色を同時に使うステージにはしない。

上記の判定・操作は「ロジックは同じ」という要望を現在の動作へ適用したもの。開始点・枠・線・禁止マーク・リロード・早見表は、そのステージの色と一致させる。今回の要望について、実装検討を進めるための追加の仕様確認事項はない。

## 2. 現状の調査結果

- `Assets/Scripts/PuzzleRules.cs` の `BaseColor` は赤・青・黄、`TileColor` は紫・オレンジ・緑まで定義済み。混色はビットの和で表現している。
- `PuzzleRules.IsTileCorrect()` は、色指定のないマスの正解を赤・青に固定している。ここは変更が必要。
- `PuzzleRules.CanAddColor()` は3色混合を拒否するが、ステージごとの使用可能な2色は管理していない。
- `Assets/Scripts/GlobalScripts.cs` は基本3色・混色3色の盤面色、線色、枠画像を扱える。既存の色定義を再利用できる。
- `Assets/Scripts/GameManager.cs` の線管理は `BaseColor` をキーとする辞書・集合で、赤・青の2色に直接固定されていない。開始点の登録前に今回の2色を確定すれば、描画処理の大部分を再利用できる。
- `Assets/Scripts/TileController.cs` は開始色・指定色・禁止色をシリアライズしている。枠表示・判定にはフィールドの直接参照もあり、プロパティだけの修正では足りない。
- 開始点・禁止マークはシーン側で色付き画像を設定している。`RefreshVisuals()` は主に表示／非表示の更新で、色に応じた画像の再選択は行っていない。
- `Assets/Scripts/GameHud.cs` の2つのリロード操作と有効状態は赤・青に固定されている。
- `Assets/Editor/StageScreenBuilder.cs` は赤・青のリロード画像と紫の早見表を設定している。早見表は1枚の画像。
- `Assets/Scripts/BoardLineRenderer.cs` は線色のビット和を用いており、黄・オレンジ・緑にも対応済み。ロジックの変更より、実際に表示されるかの検証が中心になる。
- `Assets/Scripts/StageProgress.cs` は表示番号と問題IDを分離している。Stage31以降は問題5〜30から直近8問を除いて抽選する。
- `Assets/Scripts/StageClearNavigation.cs` は入場時の表示番号を保持する。クリア後に進行番号が増えても、プレイ中のシーンの番号は変わらない。
- `GameManager.CommitLineAsync()` はクリア演出より前に `StageProgress.RecordClear()` を呼ぶ。このため保存上の番号から毎回色を計算すると、境界ステージのクリア中に色が変わってしまう。
- `Assets/Editor/ReferenceStageBuilder.cs` と `Assets/Tests/PlayMode/StageTestReference.cs` の既存問題は赤・青・紫の基準で定義されている。

## 3. 推奨する設計

### 色の選択と変換を1か所に集約する

新規の `StageColorPalette`（仮称）に、基本第1色・基本第2色・混色・使用可能色の集合と、基準色からの変換を持たせる。既存のenumの数値は変更しない。

表示番号からの選択は「(stageNumber - 1) / 5 を3で割った余り」で決まる（整数除算）。タイトルなどの表示と盤面が別々の計算規則を持たないようにする。

色の変換は表示用のRGB置換ではなく、開始色・必要な構成色・禁止する完成色を含めた意味の変換とする。`TileColor.None` はそのまま保持する。混色と禁止色は構成色の対応に沿って変換する。

現行の30問は赤・青を基準とする。今回の対象では、この基準データと実行時の色を明確に分ける。将来、黄を直接含む問題を作る場合は、基準色の役割表現を拡張して扱いを定義する。今回はその追加仕様まで広げない。

### 入場時に確定し、プレイ中は保持する

`StageClearNavigation.Awake()` が表示番号を確定した後、`GameManager.Initialize()` でその番号に対応するパレットを取得・保持する。`StageProgress.CurrentStageNumber` を毎回参照して描画や判定を切り替えない。

初期化順は「入場番号の確定 → パレットの保持 → 各タイルへ適用 → 開始点辞書の構築 → 線とHUDの更新」とする。

`GameHud.Awake()` は現在初期化前にも `Refresh()` を呼ぶため、初期化済みイベントでパレットに応じた表示を更新する。最初の表示フレームで開始点・枠・早見表・ボタンが一致するようにする。

リロードや `Initialize()` の再実行でもパレットが切り替わったり、色の変換が重なったりしないようにする。Editorからのシーン直接再生は既存の入場番号の扱いを引き継ぐ。

### 問題の基準データを保持する

シーンに保存された開始色・指定色・禁止色は変更せず、`TileController` が保持する実行時パレットを通して、判定と表示に使う色を得る方式を推奨する。現在塗られている色は実際の色で保持し、再変換しない。

`StartColor`、`RequiredColor`、`ForbiddenColor` と内部の判定・枠表示で、同じ変換結果を使う。`Configure()`、`ResetRuntimeState()`、初期化を繰り返しても、元の定義から解決する。

パレットのない独立したタイルや既存の単体テストの既定動作は赤・青とし、ステージでの動作は管理側から明示的に設定する。

### ルールの固定色を引数にする

`PuzzleRules.IsTileCorrect()` が使用可能な基本2色を受け取るようにし、通常マスがそのどちらかの単色かを判定する。単に黄を既存の赤・青の正解条件へ追加する実装は、使わない3色目も正解にしてしまうため採用しない。

色追加でも、そのパレットに含まれない基本色を拒否する。指定色との完全一致、完成色に対する禁止判定、同色の重複防止は維持する。

### HUDと素材を実際の2色に合わせる

色別リロードは既存の2枠を使い、第1色・第2色を対象とする。現在の配置を維持するなら、右側の旧赤ボタンが第1色、中央の旧青ボタンが第2色となる。見た目、クリック先、有効状態をまとめて切り替える。ALLはそのまま全色初期化とする。

早見表は紫だけでなく、そのステージの「基本色＋基本色＝混色」に切り替える。開始点・禁止マークの画像も実際の色に合わせる。

素材参照は共有の `StagePaletteVisuals` アセット（仮称）に集約し、`GameManager` からタイルとHUDへ供給する方式を候補とする。開始点などの既存素材はResources配下ではないため、Player内で `AssetDatabase` を使って取得する構成にはしない。

既存シーンへの参照追加は、問題の座標・条件を保持する専用Editor更新処理で行う。`ReferenceStageBuilder.BuildStages()` による全問再生成は、この参照追加のためには使わない。

## 6. 実装時の検証

1. Stage1、5、6、10、11、15、16、20、21、25、26、30、31、35、36、40、41で周期を確認する。
2. 各組について、通常マスは使用中の単色2色だけ正解、空白・混色・使用外の基本色は不正解であることを確認する。
3. 各組の指定色との完全一致、禁止色の完成色比較、混色から片方を除去した後の再判定を確認する。
4. 黄で線を開始・確定・リロードでき、オレンジ・緑の面、枠、共有辺・交点が一致することを確認する。
5. 既存30問がそれぞれの色の組み合わせで同じ解答経路を使ってクリアできることを、既存の問題経路データで確認する。
6. Stage31以降は問題IDと表示番号を意図的に異ならせ、問題の経路・配置と色の選択を別々に確認する。同じ問題を異なる表示番号で再利用した場合も対象にする。
7. Stage5→6、10→11、15→16、30→31、35→36、40→41のクリア演出中は現在の色を維持し、次の入場で切り替わることを確認する。
8. HOME、再入場、ALL、色別リロード、初期化の再実行、アプリ再起動で、色の組み合わせが不意に変わらないことを確認する。
9. HUDの2ボタンの色・操作対象・有効状態、早見表、開始点、禁止マークが一致し、配置と入力領域を保つことを縦画面で確認する。
10. Editorからの直接再生、旧セーブ、既存の進行・キャンセル・巻き戻しの回帰テストを確認する。テスト時のPlayerPrefs退避・復元は既存のfixtureを利用する。

## 7. 実装・検証結果
